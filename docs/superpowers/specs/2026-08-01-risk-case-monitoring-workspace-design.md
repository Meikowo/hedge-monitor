# 风险案例监控工作区设计

## 目标

在现有 GitHub Pages 研究终端左侧新增独立的“风险案例监控”工作区，把公告中的计划、
定期报告中的实际和监管文件中的风险后果串成三层研究链条。页面保持现有浅色、克制、
高信息密度的视觉语言，不改变“套保事件”“公告原流”和“计划与实际”的数据结构。

本功能分两阶段交付：先制作使用固定样例数据的本地 Demo，确认表格、筛选和详情结构；
正式风险案例达到上线质量闸门后，再接入 Supabase 并开放线上导航入口。

## 数据边界

- 风险工作区公开展示两种证据级别：`官方文件／已核实` 与 `媒体报道／未核实`。两者
  可以出现在同一列表，但数据库、数量统计、筛选、详情和导出必须始终可区分。
- 正式案例继续读取 `derivative_risk_cases`、`risk_case_documents`、
  `risk_case_evidence` 和 `risk_source_documents`，且必须形成官方证据链。
- 原始 `risk_media_leads` 与 `risk_media_backfill_windows` 继续保持 service_role 私有，
  不能直接授予 anon 读取。只有通过自动发布门槛的安全字段进入独立公开媒体投影层。
- Tavily 新闻不能独立证明正式案例，但允许作为公开的未核实研究线索。媒体行必须显著
  标注“媒体报道／未核实”，并保留媒体名称、发布日期和原文 URL。
- 页面不生成综合风险评分，不把媒体报道扩展为监管或法律定性，不展示没有来源的推测。
- 媒体原文只保留短摘要或短引文和链接，不复制整篇报道。

## 正式实施的召回与首批口径

- 首批真实案例不限定最近五年，允许覆盖可取得官方依据的任意历史年份。
- “进入官方候选层”不要求主观比较哪份证据“最完整”。只要官方原文直接涉及某家上市
  公司已发生的衍生品风险事实，即可写入 `risk_source_documents` 并进入后续复核。
- 官方依据包括交易所问询、监管措施、纪律处分，证监会及派出机构监管/处罚文件，以及
  上市公司在交易所或法定披露渠道发布的风险、损失、回复、整改和定期报告原文。
- 普通媒体、搜索摘要和二次转载不能独立进入官方候选层。它们先进入私有召回层；通过
  公开媒体门槛但暂未找到官方原文时，可以进入“媒体报道／未核实”公开投影。
- 召回采用双通道并行：一条从官方监管与法定披露来源直接扫描，另一条从 Tavily/已知
  历史线索反查官方原文。找到官方依据时归一到官方文档契约；暂未找到官方依据但通过
  媒体公开门槛时进入独立公开投影，不能写入正式案例四表。
- 第一条正式纵向切片先跑通 1—3 个真实案例的“线索—官方文档—结构化案例—逐字段
  引文回验”链路；该切片只验证管线，不降低后述 50 份官方候选和 10 个正式案例的上线
  质量闸门。
- 首批案例允许只有一份官方文件，但每个前端展示的关键事实必须能在这份或关联的其他
  官方文件中定位。官方文件只证明部分事实时，其余字段保持“未披露”，不能推断补齐。

## 媒体线索公开门槛与升级

媒体线索只有同时满足以下条件才能进入公开投影：

1. 已匹配公司主表中的上市公司代码和名称；
2. 标题或同一句局部语境同时出现衍生品业务词与已发生风险事实；
3. 排除“若、可能、一旦、预计”等假设性风险提示；
4. 具有可识别的媒体名称、发布日期和 HTTPS 原文 URL；
5. 排除论坛、股吧、社交媒体、自媒体问答和无法识别发布主体的页面；
6. 摘要仅陈述报道内容，不把媒体判断改写成监管结论。

单一合格媒体来源即可公开，但证据级别必须保持“媒体报道／未核实”。多来源命中时合并
为同一线索并展示来源数量，不据此自动改为“已核实”。找到官方原文并形成正式案例后，
列表只保留正式案例主行，原媒体报道转为补充来源，避免重复计数。被判定误报、原文失效
或来源撤回的媒体线索从公开投影撤下，但保留私有审计记录。

## 导航与页面结构

左侧工作区顺序固定为：

1. 数据看板
2. 套保事件
3. 公告原流
4. 计划与实际
5. 风险案例监控

“风险案例监控”右侧数量显示工作区全部记录数；页面内部把正式案例和媒体线索分开统计。
页面主体由四部分组成：

1. 顶部紧凑指标：正式案例数、媒体未核实线索数、涉及公司数、监管措施/处罚案例数；
2. 筛选栏：关键词、年份、风险类型、证据级别、来源机构、工具/品种、案例状态；
3. 高密度主表；
4. 按需打开的右侧证据详情抽屉。

主表默认按事件日期倒序，列为：事件日期、公司、风险类型、证据级别、工具/品种、损失
或涉案金额、监管措施、结果、来源机构、案例状态。金额保留原币种和原单位；缺失值显示
“未披露”，不能显示为 0。媒体行使用明确但克制的“媒体报道／未核实”标签。

## 详情与文档链

点击表格行后，右侧抽屉展示：

- 公司、事件日期、风险类型和事实摘要；
- 涉及工具、品种、金额、监管措施、整改或追责结果；
- 按时间排序的“问询—回复—监管措施/处罚—整改”文档链；
- 每个关键字段对应的页码、原文引文、回验状态和官方原文链接。

媒体详情不伪造官方文档链，改为展示媒体名称、发布日期、来源域名、短摘要、原文链接、
命中关键词和“尚未找到官方依据”的状态。媒体摘要使用“据某媒体报道”口径；没有官方
依据的监管措施、处理结果和金额不得补写为确定事实。

桌面端抽屉保持主表可见；移动端改为全屏详情面板。关闭详情后保留原筛选、滚动和选中状态。

## 筛选、导出与状态

- 搜索匹配公司名称、代码、摘要、品种、工具和监管结论；多个筛选条件采用交集。
- CSV 导出完整的当前筛选结果，不受当前屏幕可见行或分页限制，使用 UTF-8 BOM。
- 导出字段包含主表字段以及记录键、证据级别、核实状态、币种、单位、置信度、来源名称、
  来源日期、来源 URL、官方文档标题和引文回验状态；不导出私有原始候选或模型响应。
- 页面具有明确的加载进度、空结果、请求超时、有限重试和最终错误状态，不允许永久转圈。
- 数据库没有正式案例时，本地 Demo 仍可展示固定样例；生产导航在上线闸门前保持隐藏。

## 前端边界

- 本地 Demo 放在 `web-demo/risk-cases/`，不访问生产数据库。
- 正式接入时新增独立 `web/risk.js`，负责风险数据读取、标准化、筛选、表格、详情和导出；
  `web/app.js` 只负责共享 shell、导航和视图切换，避免继续膨胀。
- 正式前端只读取官方四表和经过清洗的公开媒体投影，绝不直接读取私有
  `risk_media_leads` 或历史窗口表。
- 正式页面复用现有 CSS token、按钮、表格、状态面板和右侧抽屉行为，仅增加风险工作区
  必需的样式，不引入框架或第三方运行时依赖。
- 现有数据看板、套保事件、公告原流和计划与实际四个视图的读取、筛选、导出和移动端
  行为必须保持不变。

## 上线质量闸门

线上入口只有同时满足以下条件才开放：

1. M6a 已形成至少 50 份真正的衍生品风险官方候选文档；
2. 分层人工抽检确认候选相关性精确率不低于 90%；
3. 至少 10 个正式案例完成入库；
4. 每个正式案例至少关联一份官方来源文档，所有前端展示的关键结论都有已回验引文；
5. 原始媒体候选表继续保持私有，公开 anon 请求无法读取；公开媒体投影只包含通过自动
   门槛的展示字段，并在所有界面明确标注未核实；
6. 风险工作区结构测试、数据转换测试、CSV 测试、真实公开 API 启动测试和移动端检查通过。

在达到闸门前，只交付本地 Demo，不向生产导航添加空入口。

## 测试与回退

- 结构测试验证导航、筛选、主表、空状态、错误状态和详情抽屉引用节点完整；
- 单元测试覆盖金额原单位保留、null 与 0 区分、数组字段、文档链排序、双层筛选、升级
  去重和 CSV；
- 公开 API 测试验证正式四表与公开媒体投影可读、私有媒体原始表不可读，且初始化在限定
  时间内结束；
- 回归测试确认公告事件与计划实际页面节点、资源版本和导出行为不变；
- 发布前记录 `main` 基线。若上线异常，使用反向提交恢复前端，不强推，不回滚或删除
  已写入的风险案例数据。
