# M6a 官方风险案例双轨扩展设计

## 决策与范围

本切片采用“案例发布与来源扩展并行、准入门槛分离”的双轨方案：

- 轨道 A 将已经通过巨潮官方 PDF 原文回验的台华新材、焦作万方案例发布到正式风险案例库，使官方案例由 3 条增加到 5 条。
- 轨道 B 将上交所与深交所的问询函、监管措施等官方文件接入统一候选文档层，为后续案例扩展建立可持续来源。
- 新交易所文档只能写入 `risk_source_documents`，不得由采集器直接生成 `derivative_risk_cases`。
- 证监会及地方证监局来源不在本切片实现。其页面结构和发布主体更分散，待交易所双来源稳定后单独设计适配器。
- 不修改正式前端字段、数据库表结构、RLS、媒体候选层、公告抽取或年报管线。

50 份官方候选、10 个正式案例和候选精确率不低于 90% 仍是 M6a 的扩量里程碑，不是本切片的完成门槛。

## 方案比较

### 采用：双轨、分层准入

已回验案例立即发布；新来源只生产候选，经过后续证据回验与独立发布步骤后才能升级为正式案例。优点是能够同时增加可见成果和长期召回能力，并保持正式案例证据标准不变。

### 未采用：只扩充巨潮案例

这一路径最快，但目前严格规则只额外召回 2 条，且难以覆盖问询函、监管措施和纪律处分，无法解决来源偏窄问题。

### 未采用：上交所、深交所、证监会一次性接入

来源覆盖最广，但证监会及派出机构页面异构度高，会把接口适配、历史分页、正文解析和案例准入同时耦合，故障定位和质量抽检成本过高。

## 架构与组件边界

### 轨道 A：新增案例发布

沿用 `scripts/publish_official_risk_cases.py` 的严格巨潮公告规则和 PDF 逐字回验。发布器在应用 `limit` 前读取已存在的 `cninfo:*` 来源或稳定 `case_key`，跳过已发布案例，再从未发布候选中选择新案例。这样每日任务不会被既有 3 条反复占满名额。

台华新材与焦作万方的金额、日期、公司代码、风险类型和引文均以已经回验的官方 PDF 为准。缺失字段继续保持空值，不用媒体或模型推断补齐。写入仍按 `source_doc_id`、`case_key` 及关系键幂等 upsert，证据按稳定签名避免重复插入。

### 轨道 B：官方来源候选池

保留“来源适配器只负责发现与归一、统一采集器负责正文与业务闸门”的边界：

- `scripts/risk_sources/sse.py`：继续负责上交所分页、JSON/JSONP 解包、URL 和字段归一。
- `scripts/risk_sources/szse.py`：新增深交所适配器，使用实施时验证可用的深交所官方公开页面或接口，负责分页、日期窗口、礼貌限速和字段归一。
- `scripts/fetch_risk_documents.py`：通过明确的来源注册表按 `--source sse|szse|all` 调用适配器，统一下载 HTML/PDF、提取文本、运行确定性相关性闸门、去重、生成快照和可选写库。

每个适配器输出相同契约：`source_doc_id`、`source_org`、`source_type`、`official_doc_id`、公司代码与名称、标题、发布日期、官方 HTTPS URL、格式及原始元数据。稳定主键分别使用 `sse:<官方ID>` 和 `szse:<官方ID>`。

本切片不建立通用插件框架。来源注册表保持显式、短小，后续接入证监会时再增加一个适配器和注册项。

## 数据流与状态

```text
上交所／深交所官方索引
        ↓ 来源适配器归一
官方文档元数据
        ↓ 正文下载与文本提取
确定性衍生品风险闸门
        ├─ candidate  → risk_source_documents（待证据复核）
        ├─ irrelevant → risk_source_documents（保留排除依据）
        └─ failed     → risk_source_documents（保留失败摘要，可重试）

巨潮已抽取公告
        ↓ 严格实际损失规则
官方 PDF 逐字回验
        ↓ 排除已发布案例后应用批次上限
正式案例四表
```

状态语义固定如下：

- `discovered`：只完成元数据发现，尚未完成正文读取；
- `candidate`：正文已读取，衍生品业务词与已发生风险信号通过同一语境闸门；
- `irrelevant`：正文已读取，但只命中通用制度、会计政策、普通经营风险或其他非衍生品语境；
- `failed`：索引请求、正文下载或正文解析失败，并保存不含密钥的错误摘要；
- `relevant`、`extracted`：仅由后续证据复核与正式案例发布流程使用，采集器不得直接设置。

交易所候选不得调用 MiniMax，也不消耗 LLM 配额。后续若候选数量足够，再单独设计候选复核和正式案例结构化步骤。

## 调度与历史范围

- 新增或调整独立官方来源工作流，继续使用 `risk-sources` 并发锁，不占用巨潮公告与年报使用的 `cninfo` 并发锁。
- 每日北京时间 10:10 扫描最近 30 个自然日，使用重叠日期窗口并依赖 `source_doc_id` 幂等去重，避免接口延迟发布造成漏采。
- 手动入口允许指定来源、起止日期、最大页数、正文读取和写库开关；写库必须保留明确确认项。
- 历史回填按年度或较短日期窗口显式运行，不在一个任务中一次扫描几十年。若官方接口存在历史覆盖上限，快照必须记录实际处理边界，不把“接口无结果”表述为“历史无案例”。
- 单一来源失败不得取消另一来源已经完成的结果；每个来源单独输出发现数、候选数、排除数、失败数和快照文件。

## 正式案例准入

交易所候选只有同时满足以下条件，才能在后续发布步骤升级为正式案例：

1. 原文直接指向目标上市公司，代码或名称可核对；
2. 原文直接涉及该公司的套期保值、期货、期权、远期、掉期或其他衍生品业务；
3. 原文披露已发生的损失、超授权、投机偏离、内控缺陷、保证金或流动性问题、会计或信息披露问题、问询、处罚或整改事实；
4. 每个关键字段均有官方 URL、页码或段落及可逐字回验引文；
5. 普通汇兑损失、通用会计政策、风险提示和公司曾经开展套保但本文件无风险事实的记录不得升级。

媒体报道仍可按既有规则以“媒体报道／未核实”展示，但不能替代上述官方证据或补写缺失字段。

## 错误处理与安全

- 索引请求和正文请求分别进行有限次数重试与退避；最终失败写 `failed`，不得静默跳过。
- PDF/HTML 设定大小和超时上限；保存正文哈希、字符数、官方 URL 和原始接口元数据，避免保存完整受版权保护正文到公开表。
- 快照和日志不包含 Supabase 密钥、Tavily 密钥或完整请求头。
- `risk_source_documents` 继续使用现有 RLS 和只读公开权限；本切片不新增表，也不扩大浏览器权限。
- GitHub Actions 只从 Repository Secrets 读取凭据，发布文件不包含 `.env`。

## 测试与验收

### 离线测试

- 官方发布器：已发布案例不会占用新增批次名额；重复运行不新增关系或证据；台华新材和焦作万方金额与引文口径保持稳定。
- SSE/SZSE 适配器：分页、日期参数、URL 规范化、文档 ID、公司字段、HTML/PDF 格式和异常响应。
- 统一采集器：`sse`、`szse`、`all` 路由，跨来源去重，四种状态转换，单来源失败隔离和写库幂等。
- 相关性闸门：明确衍生品风险、普通经营问询、通用政策、普通汇兑损失及公司身份不一致。

### 真实只读与生产验收

1. 上交所和深交所官方公开来源各完成一次真实只读探针，输出可审计快照；
2. 写库模式重复运行后，候选文档数量不因重复扫描而虚增；
3. 官方案例由 3 条增加到 5 条，台华新材和焦作万方在正式网站可见，来源与引文可打开；
4. 新交易所文档只进入 `risk_source_documents`，正式案例数不会因候选采集自动增加；
5. 正式前端、公告事件、数据看板、计划与实际、CSV 和风险详情回归通过；
6. Supabase Security Advisor 保持 0 告警，匿名用户不能写入风险表；
7. 更新 `PROJECT.md` 和阶段工作日志，记录实际发现数、候选数、失败数、提交及回退基线。

如果某一交易所在测试窗口内没有相关文档，只要分页边界、请求结果和零候选结论可审计，该来源的链路验收仍可通过；不得为了达到数量目标降低相关性门槛。

## 发布与回退

- 代码、测试、工作流和文档组成一次原子 GitHub 提交，使用 GitHub 插件对 `main` 做非强制快进；远端基线变化时停止并重新核对，不强推。
- 数据写入顺序为：先运行官方案例发布预演，再发布 2 个新增案例；随后分别运行 SSE、SZSE 候选采集预演，最后才执行候选写库。
- 代码异常通过反向提交回退；候选文档为幂等派生数据，可按稳定来源键重新采集。正式案例不物理删除，如证据发现问题则另行标记复核状态并保留审计链。
