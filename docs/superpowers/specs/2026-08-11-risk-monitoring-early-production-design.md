# 风险案例监控提前上线设计

## 决策与目标

风险案例监控不再等待“50 份官方候选、10 个正式案例”后才开放导航。用户已确认采用
“严格筛选后提前上线”：正式网站先如实展示当前可公开的数据，官方案例为 0 时明确显示
0，不使用 Demo 虚构数据填充；后续官方案例与合格媒体记录沿现有自动管线持续增加。

本设计只提前开放风险研究工作区，不降低官方案例的证据标准。旧设计中的 50/10/90%
指标继续作为 M6 官方管线规模化验收目标，不再作为前端入口的硬开关。

## 数据边界

- 浏览器只读取公开官方四表 `risk_source_documents`、`derivative_risk_cases`、
  `risk_case_documents`、`risk_case_evidence`，以及公开媒体投影
  `risk_media_reports`、`risk_media_report_sources`。
- 私有 `risk_media_leads` 与 `risk_media_backfill_windows` 继续仅允许后台
  `service_role` 读取；前端代码、CSV 和错误日志都不得包含这些表的字段或请求。
- 官方记录统一标记“官方文件／已核实”；媒体记录统一标记“媒体报道／未核实”。媒体
  不能生成监管结论，也不计入正式案例数。
- 找到官方原文并形成正式案例后，正式案例成为主行，原媒体来源作为补充来源，不重复
  计算同一事件。
- 公开媒体记录保留短摘要、具名发布者、日期、域名和 HTTPS 原文链接，不保存或展示
  Tavily 评分、原始元数据、完整文章和内部复核字段。

## 媒体质量修复

公开发布器在现有同句衍生品词与风险词条件上增加以下确定性校验：

1. 公司名称或证券代码必须出现在标题或被采用的风险语境中；标题含其他公司名称或代码
   时拒绝，避免惠科股份文章被错配为包钢。
2. 只接受已经发生的公司特定事实；风险提示、可行性分析、管理制度、免责声明、一般
   行业评论和“若、可能、存在……风险”等假设性描述拒绝。
3. 损失类记录必须在同一局部语境中明确连接衍生品工具与已发生损益，并至少包含明确
   数额、比例、重大性表述或爆仓／强平等结果。仅“发生汇兑损失，同时公司开展套保”
   不足以证明衍生品风险。
4. 搜索页面的通用交易风险免责声明、基金文件、非目标上市公司、期货公司自身经营新闻
   和公司匹配失败的结果不得公开。
5. 每次发布不仅增加新记录，还重新评估现有公开投影。未通过新规则的记录改为
   `dismissed`，保留私有审计，不做物理删除。

首轮存量处理固定为：保留江特电机与仙乐健康两条“媒体报道／未核实”；将玲珑轮胎的
一般汇率分析和错误匹配为包钢的惠科股份风险提示撤出公开投影。若实施时来源内容或公司
事实与本设计不一致，停止该条状态更新并记录证据，不扩大推断。

## 正式前端

- 左侧导航在“计划与实际”之后增加“风险案例监控”，不改变其他四个工作区。
- 新增独立 `web/risk.js`，负责公开风险数据分页读取、标准化、去重、筛选、表格、详情
  和 CSV；`web/app.js` 只接入导航和共享加载状态。
- 顶部指标显示官方案例数、媒体未核实数、涉及公司数和监管措施／处罚案例数。官方案例
  为空时显示 `0`，不隐藏整个页面。
- 筛选包含关键词、年份、风险类型、证据级别、来源机构和案例状态；条件取交集。
- 高密度主表按事件日期倒序，列示日期、公司、风险类型、证据级别、工具／品种、金额、
  监管措施、结果、来源和状态。缺失金额显示“未披露”，绝不显示为 0。
- 右侧详情抽屉：官方记录展示事实摘要、文档链、逐字段引文和回验状态；媒体记录只展示
  来源、短摘要、命中工具／风险词和“尚未找到官方依据”。
- CSV 导出当前完整筛选结果并带 UTF-8 BOM，包含证据级别与来源，不包含私有候选。
- 桌面端保持主表可见，移动端详情为全屏；复用当前浅色、高密度、少装饰的设计语言。

## 加载与错误处理

- 公开六表分别分页请求；单次请求 20 秒超时，失败最多重试 3 次，并显示已读取数量。
- 官方表为空属于正常状态，不是错误；任一数据域失败时显示具体表名和重试入口，不永久
  转圈，也不把另一数据域已成功读取的数据清空。
- 正式案例与媒体来源在客户端按稳定键归并；孤立子记录忽略并计入诊断，不生成空主行。

## Supabase 权限

- 六张公开表全部保持 RLS 启用。
- `anon` 与 `authenticated` 对公开表只保留 `SELECT`；撤销 INSERT、UPDATE、DELETE、
  TRUNCATE、REFERENCES 和 TRIGGER 等不需要的权限。
- `service_role` 保留后台管线所需的读写权限。
- 私有媒体两表继续不向 `anon` 或 `authenticated` 授予任何权限，并用真实匿名请求验证
  返回拒绝。
- 权限修复使用可重复执行的仓库 SQL 迁移并同步 `db/verify.sql`，不更改现有业务数据。

## 测试与发布

- 测试先行覆盖：公司错配、假设性风险、免责声明、一般汇兑损失、明确衍生品损失、存量
  撤回和重复运行幂等。
- 前端逻辑测试覆盖双数据层标准化、官方优先去重、null 与 0、筛选、CSV 和详情抽屉。
- 结构测试覆盖导航、指标、筛选、表格、空状态、错误状态和移动端所需节点。
- 真实匿名 API 启动测试验证公开六表可读、私有两表不可读，并在 60 秒内完成初始化。
- 发布前运行完整 Python 与 Node 回归、Supabase Security Advisor、精确文件密钥扫描和
  线上 GitHub Pages 验证。
- 记录发布前 `main` 提交。通过 GitHub 插件创建原子提交并以 `force=false` 快进 `main`；
  若基线变化则停止核对，不强推。异常回退使用反向提交，不删除数据库记录。

## 完成标准

1. 正式域名出现“风险案例监控”入口并读取真实 Supabase 数据；
2. 误报记录不再公开，首版数据均明确标注证据级别；
3. 官方案例为 0 时页面仍能正常加载、筛选和导出；
4. 私有媒体候选无法被匿名浏览器读取；
5. 公告、数据看板、计划与实际及现有导出功能全部回归通过；
6. 工作日志与 `PROJECT.md` 记录数据数量、规则变更、提交和回退基线。
