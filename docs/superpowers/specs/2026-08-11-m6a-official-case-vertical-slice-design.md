# M6a 官方案例纵向切片设计

## 目标与范围

本切片把已经进入 `announcements`、并由 MiniMax 写入 `extractions` 的巨潮官方公告，严格投影到风险案例官方四表。首轮只发布最新 3 个具备“已发生衍生品损失 + 官方原文引文”的案例，不重新调用模型、不依赖手工录入。仅对最终入选的 3 份 PDF 重新下载一次，用于程序化核对引文确实存在于官方原文。

首批目标案例为江特电机、豪森智能和天宇股份。管理制度中的假设性亏损阈值、未发生亏损、普通汇兑损失以及只有媒体描述的记录一律排除。

## 数据流

1. 从 `announcements` 与 `extractions` 读取 `is_hedge_related=true` 的公告。
2. 只接受 `ann_role` 为“进展”或“风险提示”，且证据引文明确包含已经发生的亏损事实。
3. 下载入选 PDF，用与公告抽取一致的文本归一化规则回验损失引文；回验失败的记录不得写入正式表。
4. 将公告标准化为 `risk_source_documents`，来源固定为 `CNINFO`，文档 ID 为 `cninfo:<ann_id>`。
5. 生成稳定案例键 `<code>|<ann_date>|重大衍生品损失|official`，写入 `derivative_risk_cases`。
6. 用 `risk_case_documents` 关联官方公告；把损失、工具、品种与摘要引文写入 `risk_case_evidence`。
7. 若同公司媒体记录对应同一事件，更新为 `officially_corroborated` 并关联正式案例；前端继续以官方案例为主行。

四表按主键幂等 upsert。任一步中断后重跑可恢复，不删除现有记录。

## 字段口径

- 风险类型：`重大衍生品损失`。
- 金额：只从明确的实际损失引文解析；“超过一千万元”一类阈值不当作精确金额，数据库保持 `null`。
- 币种与单位：金额可解析时使用 `CNY` 与 `万元`；否则保持 `null`。
- 状态：首批官方公司公告记为“进行中”，`need_review=true`；官方引文程序回验通过，但金额值仅在精确解析成功时标记回验。
- 监管措施：公司风险公告本身不等于监管处罚，保持“未见监管措施”。
- 处理结果：原文未披露时保持“待后续公告或定期报告确认”。

## 运行方式与安全边界

新增独立 GitHub Actions，支持手动 dry-run/write，并在每日公告抽取完成后定时运行。写库仍只使用 `service_role`；浏览器权限、RLS 和现有六张公开表不变，不需要数据库结构迁移。

工作流默认每批最多发布 3 个新案例。重复运行只更新同一稳定键，不重复计数。快照只包含官方公开字段，不包含密钥或私有媒体候选。

## 验收标准

1. 规则测试能排除制度阈值、未亏损和普通汇兑损失，并接受明确实际衍生品亏损。
2. 三个首批案例均写入官方四表，每个案例至少有一条官方损失引文。
3. 江特电机媒体记录与官方案例关联，正式前端不再重复显示同一事件。
4. 真实公开 API 能读取 3 个官方案例，私有媒体表仍不可读。
5. 完整 Python、Node、Security Advisor 和 GitHub Actions 验证通过。
