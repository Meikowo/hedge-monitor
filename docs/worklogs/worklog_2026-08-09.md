## 年报扩量停滞根因

- `Periodic Reports Formal` 发布后连续 5 次定时任务失败。最新 Run #44 在第一个
  `Report formal progress before batch` 步骤读取正式池时触发 `UnicodeDecodeError`，
  因此元数据发现、页面定位和 LLM 提取均被 GitHub Actions 跳过。
- 本地 `config/annual_formal_2025.csv` 为 317,184 字节、原始字节 Git Blob
  `f690a95f7f39880e3f955d5313d48502ba78a460`；远端仅约 46,644 字节、Git Blob
  `2372b76ffa0bea3b7fa7e2b8f1c181b601e77de1`。
- 同一发布链路还截断了 `docs/PROJECT.md`、`scripts/extract_periodic_reports.py` 和
  `tests/test_periodic.py`。小文件哈希一致，说明根因不是源文件或 GitHub Actions，
  而是发布时把大文件一次性经过了有输出长度限制的本地中间层。

## 修复原则

- 不修改数据库、年报字段契约、抽取口径或批量参数。
- 从本地完整文件按固定字节块读取；各块在内存中重组 Base64 后调用 GitHub 插件
  `create_blob`，不再把整份大文件作为单次终端输出传递。
- 更新 `main` 前要求 GitHub 返回的 Blob SHA 与本地
  `git hash-object --no-filters` 完全一致，避免 Windows 换行过滤造成误判。
- 发布后先验证远端 UTF-8、1,812 行正式池和完整测试，再观察 Actions 是否越过进度步骤。
